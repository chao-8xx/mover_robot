# 机器人／运动控制方向简历项目素材

用途：从维护文档提炼项目介绍、候选职责和面试证据。本文件不是已核实的个人简历。当前只确认求职方向为机器人／运动控制，个人负责模块、实车指标、比赛成绩和项目起止时间尚未提供。

## 1. 项目名称与概述

建议名称：**基于 STM32 的视觉辅助物料搬运机器人**。

项目概述候选：基于 STM32F407VET6、麦克纳姆轮底盘和闭环步进驱动器，构建面向比赛物料搬运的控制系统；软件包含栅格路径搜索、IMU 航向控制、视觉偏差对准、升降/伸缩/夹爪/转盘动作协调及人机交互。

技术关键词可按实际掌握选择：C、STM32 HAL、UART/DMA、定时中断、状态机、PID、麦克纳姆轮运动解算、IMU、MaixCAM、OpenMV、Python、CMake、主机回归测试。

## 3. 三条候选简历表述

确认个人职责后，可以从下列候选中选 2～3 条压缩使用，不要整段照搬成已完成个人成果：

1. 参与基于 STM32F407 的麦克纳姆轮底盘控制开发，实现四轮运动指令解算、位置目标同步启动及 IMU 航向 PID 控制，并进行轮径/横移补偿参数维护。
2. 参与视觉辅助抓放控制，将相机图像偏差映射为底盘及伸缩机构控制量，通过分层状态机协调行驶、升降、夹爪、云台与转盘动作。
3. 参与串口协议与驱动维护，采用 DMA 发送队列、视觉结果去重/超时机制和主机回归测试支持模块联调及问题定位。

若个人主责是导航，可替换其中一条为：开发基于道路图和可信位姿的分段导航模块，包含道路状态检查、停稳观察、实际到位确认和异常停止；使用主机测试验证控制逻辑。当前只能说明模块实现与主机验证，不能写成已完成实车自主避障。

上述句子暂未使用“提升 X%”“定位误差 X mm”“稳定 X Hz”等量化说法。代码阈值和调度周期不能代替实测结果。

## 4. 目前表述边界

| 代码事实 | 应如何表达 |
| --- | --- |
| 位置模式装填四台电机后广播触发 | 多电机同步启动；不要写多机器人协同 |
| 定时中断与主循环共同调度 | 裸机周期服务/状态机；不要写 FreeRTOS 多任务 |
| bfs 命名接口实际做带转弯代价的加权搜索 | 加权栅格路径规划；不宣称已证明方向扩展图的全局最优 |
| 视觉偏差进入 PID | 基于图像误差的视觉辅助对准；没有标定证据时不写毫米级视觉定位 |
| 编码器/IMU 增量里程计实现存在 | 航迹推算模块；不要写成已验证的多传感器融合定位或 SLAM |
| 独立 map_nav 主机检查通过 | 模块级验证；不等同整车接入或道路实测 |
| NOW 157 项测试通过 | 视觉电脑回归结果；不等同板端帧率、识别成功率或当前主控通信开启 |
| 当前主控 camera/odom 测试失败 | 持续维护中的已知问题；不能写全项目回归全部通过 |

## 6. 面试准备

围绕自己负责的条目准备一段能展开的解释：

1. 为什么控制脉冲 3200/圈和编码器完整反馈 65536/圈不能共用换算？
2. 四轮命令逐条发送如何做到同步启动？队列失败时还缺什么确认？
3. PID 的 Ki/Kd 为什么依赖调用周期？角度复位怎样影响旧目标？
4. 图像 X/Y 为何交换轴并取负号？它与相机/车体安装有什么关系？
5. 软件 busy 结束与机械实际到位有什么区别？如何验证超时退出？
6. 主机测试替代了哪些硬件依赖，哪些结论必须留给设备和实车验证？

选择一个真实调试案例，按“现象 → 分层排查 → 根因证据 → 改动 → 重复验证”讲清楚，通常比罗列更多算法名称更有说服力。
